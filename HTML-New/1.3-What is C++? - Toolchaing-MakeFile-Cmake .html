Chapter 0 — C++

What is C++?

C++ is a compiled, statically-typed, multi-paradigm programming language created by Bjarne Stroustrup (1979, Bell Labs) as "C with Classes."

It gives you:

  • Low-level control (memory, hardware) like C
  • High-level abstractions (classes, templates, RAII) like modern languages
  • Zero-cost abstractions — you don't pay for what you don't use
Why does it exist?
Problem before C++ What C++ added
C is fast but has no OOP Classes, inheritance, polymorphism
Manual memory everywhere Constructors/destructors (RAII)
Code reuse is painful Templates, STL
Large projects get unmaintainable Namespaces, strong typing

    B -->|Compiler| C[hello.s]

    D -->|Linker + libs| E[hello executable]
    E -->|Loader| F[Running process]

    │  ./hello
    ▼

Stage 1 — Preprocessor

The preprocessor is a text replacer. It does NOT understand C++.

Directives it handles:

Directive Purpose
#include Paste file contents here
#define Textual macro substitution
#ifdef #ifndef #endif Conditional compilation
#pragma Compiler-specific hints 
#define PI 3.14159
#define SQUARE(x) ((x)*(x))

g++ -E hello.cpp -o hello.i
head -50 hello.i   # see the giant expansion from <iostream>

//⚠️ Warning: Macros are dangerous — no type checking, weird side effects.
#define SQUARE(x) x*x
SQUARE(2+3)   // → 2+3*2+3 = 11, not 25!

//Always parenthesize: #define SQUARE(x) ((x)*(x)) — but prefer inline functions / constexpr
Stage 2 — Compiler

  • Translates preprocessed C++ into assembly for the target CPU.

        g++ -S hello.cpp -o hello.s

  • What the compiler does:

    • Lexing → tokens
    • Parsing → AST
    • Semantic analysis → type checking
    • Optimization → -O0, -O2, -O3
    • Code generation → assembly

  • 🎯 Interview Point: "Why is C++ compiled?"

    • Because the compiler translates the whole program to machine code ahead of time (AOT), giving predictable performance and no runtime interpreter overhead.
Stage 3 — Assembler

Turns .s into .o — machine code, but with unresolved references.

g++ -c hello.cpp -o hello.o

An object file contains:

  • Code section (.text)
  • Data section (.data, .bss)
  • Symbol table (names of functions/variables — some defined, some referenced)
#Check symbols:
nm hello.o
# U std::cout      ← U = undefined (imported)
# T main           ← T = defined in .text
Stage 4 — Linker 🔥

The linker joins object files + libraries into one executable and resolves symbols.

Two kinds of linking:

Kind When Effect
Static (.a) Link time Library code copied into binary — bigger but self-contained
Dynamic (.so/.dll) Runtime Binary references library; loader loads it at startup 
# static
g++ main.o -static -o app
# dynamic (default)
g++ main.o -o app

Common linker errors

undefined reference to 'foo()'
Meaning: you declared foo but never defined it, or you forgot to link the .o / library.

🔥 Senior Insight: The ODR (One Definition Rule) lives here. If two .cpp files define the same non-inline function with different bodies, you can get a silent link-time mismatch — no error, wrong function used at runtime. Keep definitions in .cpp, declarations in .h.

Try it live
# all stages in one command
g++ -Wall -Wextra hello.cpp -o hello

# see every stage
g++ -save-temps hello.cpp -o hello
ls hello.*   # hello.i hello.s hello.o hello.cpp

# Files
# ============================================================

OBJECTS      := $(SRCS:.cpp=.o)
PREPROCESSED := $(SRCS:.cpp=.i)
ASSEMBLY     := $(SRCS:.cpp=.s)

# ============================================================
# Main Build
# ============================================================
#.PHONY: tells it "Don't ask about a file—just execute this target."
.PHONY: all preprocess compile assemble link run clean

all: preprocess compile assemble link
	@echo ""
	@echo "======================================"
	@echo "   BUILD COMPLETED SUCCESSFULLY"
	@echo "======================================"

# ============================================================
# 1. PREPROCESSOR
# .cpp → .i
# ============================================================

preprocess:
	@echo ""
	@echo "======================================"
	@echo "1. PREPROCESSOR"
	@echo "======================================"
# $(foreach variable,list,text)
# $(SRCS) = main.cpp student.cpp calculator.cpp
# $(PREPROCESSED) = main.i student.i calculator.i
# $(foreach src,$(SRCS),COMMAND)
# src = main.cpp ==> $(CXX) $(CXXFLAGS) -E main.cpp  -o main.i
# src = student.cpp
# src = calculator.cpp
# COMMAND= $(CXX) $(CXXFLAGS) -E $(src) -o $(src:.cpp=.i)
	$(foreach src,$(SRCS),$(CXX) $(CXXFLAGS) -E $(src) -o $(src:.cpp=.i);)

# ============================================================
# 2. COMPILER
# .i → .s
# ============================================================

compile: preprocess
	@echo ""
	@echo "======================================"
	@echo "2. COMPILER"
	@echo "======================================"

	$(foreach src,$(PREPROCESSED),$(CXX) $(CXXFLAGS) -S $(src) -o $(src:.i=.s);)

# ============================================================
# 3. ASSEMBLER
# .s → .o
# ============================================================

assemble: compile
	@echo ""
	@echo "======================================"
	@echo "3. ASSEMBLER"
	@echo "======================================"
	$(foreach src,$(ASSEMBLY),$(CXX) $(CXXFLAGS) -c $(src) -o $(src:.s=.o);)

# ============================================================
# 4. LINKER
# .o → executable
# ============================================================

link: assemble
	@echo ""
	@echo "======================================"
	@echo "4. LINKER"
	@echo "======================================"

	$(CXX) $(OBJECTS) -o $(TARGET)

# ============================================================
# Run
# ============================================================

run: all
	@echo "Running $(TARGET)..."
#	./$(TARGET)
	@gnome-terminal --title="Debugging $(TARGET)" -- bash -c "./$(TARGET); echo ''; read -p 'Press Enter to close...' var"

# ============================================================
# Clean
# ============================================================

clean:
	@echo "Cleaning..."
	rm -f $(TARGET) $(OBJECTS) $(PREPROCESSED) $(ASSEMBLY)

1. علامة = (التقييم الكسول / المتأخر - Deferred)
الفكرة: بتحفظ "النص" زي ما هو ومش بتفكر في قيمته غير لحظة الاستخدام الفعلي للمتغير.
المشكلة: لو المتغير بيعتمد على دوال بحث (زي wildcard)، الـ Makefile هيفضل يبحث في الملفات ويعيد الحساب كل مرة بتنادي فيها على المتغير، وده بيبطئ الأداء في المشاريع الكبيرة.

2. علامة := (التقييم الفوري - Simply Expanded)
الفكرة: بتحسب القيمة وبتخزنها مرة واحدة فقط أول ما الـ Makefile يقرا الملف، ومش بتتغير بعد كده.
المميزات: أسرع بكتير، وأكثر أماناً واستقراراً، وعشان كده دي الطريقة المفضلة والاحترافية (Best Practice) في أغلب المتغيرات.

استعمل := للمتغيرات العادية والملفات والـ Flags (لأنها أسرع وأضمن).
استعمل = نادراً لو محتاج المتغير يتأخر في تقييم قيمته لحد آخر لحظة لأسباب معينة.

# ============================================================

# ============================================================

# patsubst = Pattern + Replacement + List

#    │
#    ├── Pattern       → الشكل القديم
#    ├── Replacement   → الشكل الجديد
#    └── Text          → الملفات اللي هنطبق عليها

Why Makefiles aren't enough for big projects

  • Hard to express "compile all .cpp in this folder"
  • Platform-specific
  • You write the whole dependency graph by hand
        main.o: main.cpp engine.hpp network.hpp
    engine.o: engine.cpp engine.hpp math.hpp config.hpp
    network.o: network.cpp network.hpp socket.hpp
  • No built-in package management (Build the project Not Manage the project's dependencies.)
CMake — the modern standard

CMake is a meta-build system: it reads CMakeLists.txt and generates Makefiles (or Ninja, or Xcode, or VS).

Project Structure

my_project/
├── CMakeLists.txt        ← Main CMake configuration file
├── include/              ← Header files
│   └── helper.hpp
├── src/                  ← Source files
│   ├── main.cpp
│   └── helper.cpp
└── build/                ← Build directory(make it Automatically)

الـ CMake مش هو اللي بي compile الكود بنفسه، ده هو "المهندس" اللي بينظم المشروع وبيطلعلك الـ Makefile (أو ملفات Visual Studio لو على Windows) بشكل اووماتيكي ونظيف جداً.
ليه الطريقة دي ممتازة ومفضلة عالمياً؟
مش مرتبط بنظام تشغيل: نفس ملف CMakeLists.txt يقدر يطلعلك مشروع لـ Linux (Makefiles) أو Windows (Visual Studio) أو macOS (Xcode) من غير ما تغير فيه حاجة.

فصل ملفات البناء: كل ملفات الـ Object والزبالة بتنزل جوه مجلد build، فبيفضل الكود بتاعك نظيف ومناسب للـ Git.
التحديث التلقائي (CONFIGURE_DEPENDS): أي ملف .cpp أو .hpp جديد هتضيفه جوه مجلد src أو include، الـ CMake هيحسه أوتوماتيك ومش هتضطر تعدل الملف الإعدادات كل شوية.

mkdir build && cd build
cmake ..        # generates build files
cmake --build . # or: make / ninja

#CMakeLists.txt

#Minimum CMake version required(The project requires at least CMake version 3.12.)
cmake_minimum_required(VERSION 3.12)

#It defines Project Information:
#- Project name → test
#- Project version → 1.0
#- Programming language → CXX = C++
project(test VERSION 1.0 LANGUAGES CXX)
#Compile the project using the C++17 standard.
set(CMAKE_CXX_STANDARD 17)
#C++17 is required. Do not silently fall back to an older C++ standard.
#C++17 Not optional it is requirement.
set(CMAKE_CXX_STANDARD_REQUIRED ON)

#"1. Define header file locations"
include_directories(${CMAKE_CURRENT_SOURCE_DIR}/include)

#2. "GLOB_RECURSE searches recursively for files matching a pattern."
#2. "Find all .cpp files inside src and all of its subdirectories."
file(GLOB_RECURSE SOURCES CONFIGURE_DEPENDS "src/*.cpp")

# 3. "Building the Executable File"
add_executable(${PROJECT_NAME} ${SOURCES})
