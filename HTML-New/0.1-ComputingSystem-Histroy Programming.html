Basics of Programming

0. Big Picture

This lesson answers one question: what really happens between the code I write and the machine that runs it? Every language, tool and error message you meet later sits on top of the answer.

What is it? The foundations every programmer needs: the computer itself, the software layers on top of it, and the ways code gets turned into something the CPU can run.

Why does it exist? Most beginners learn syntax first and are lost the first time something breaks outside their code: command not found, missing DLL, JRE not found, a program that works on Linux but not on Windows. These are not language problems. They are system problems.

What was there before? One program per machine, written in machine code, talking straight to the hardware. Change the hardware and you rewrite the program. Everything in this lesson (OS, C, Java, Python) is a layer that was added to stop that pain.

Who uses it? Everyone. Embedded engineers feel it in every line. Web developers feel it when a deployment fails.

🧠 Remember: every layer exists to hide something below it. Learn what each layer hides and why.

What students should know first

  • How to use a computer and a terminal at a basic level
  • Nothing else. We start from zero.

What students will understand at the end

  • What the parts of a computer do and why they have those names
  • What happens from the power button until an app starts
  • Why we need an OS and how code talks to it
  • Why C code is not "write once, run anywhere" and Java is
  • The real difference between compiled, interpreted and JIT
  • Why "Python is interpreted" is an incomplete sentence

1. Chapter 1 — What Is a Computing System?

  • الـ Computing System هو نظام يستقبل Input، يعالج البيانات، يخزنها عند الحاجة، ثم ينتج Output.
 Input ─────► Computing System (Processing) ─────► Output
  • A computing system is a machine that takes input, processes it by running instructions, keeps data somewhere, and produces output. It has three groups of parts: CPU, memory, and I/O.

Notes : Every program you will ever write is just a sequence of instructions that the CPU executes, using RAM as its workspace, reading/writing I/O devices, and persisting data to Disk.

CPU
  • The CPU (Central Processing Unit) is the component that executes instructions.
  • The CPU repeats one loop forever: fetch an instruction from memory, decode it, execute it. It has a few tiny, very fast storage slots called registers. Everything the CPU does happens on registers.
  • The Fetch–Decode–Execute cycle (runs billions of times per second):
   ┌──────────┐
   │  Fetch   │──► get next instruction from memory(Get instruction from memory)
   └────┬─────┘
        ▼
   ┌──────────┐
   │  Decode  │──► what does this instruction mean?(Figure out what it means)
   └────┬─────┘
        ▼
   ┌──────────┐
   │ Execute  │──► do it (add, move, jump, read, write)
   └────┬─────┘
        └──────── (repeat, forever, ~3 GHz = 3 billion times/sec)
Memory: RAM and ROM
  • 🧠 Remember: RAM = temporary workspace. ROM = permanent boot instructions.

important Notes

  • Q: Why is RAM called "Random Access" Memory, and what does "random" actually mean in this context?
    • "Random Access". The word random does not mean unpredictable. It means you can jump to any address directly and it takes the same time. Compare it to a tape: to reach song 10 you must wind through songs 1 to 9. That is sequential access. RAM has no winding.
  • How can we call Flash memory "ROM" (Read Only Memory) while we can easily write on it...?!
    • The "Read-Only" designation is relative to the Processor (CPU) at runtime. Unlike RAM, which the processor can randomly access and write to directly via its system buses (Address, Data, Control), the processor cannot directly perform standard write/erase cycles to Flash memory without specialized protocols, controllers, or drivers.
Disk

  • In everyday talk people say "my laptop has 512 GB of memory" and mean the disk. In computer architecture that is wrong.

  • Memory (RAM, ROM) sits on the memory bus. The CPU can read any byte by address, directly.

  • The hard disk / SSD is an I/O device. The CPU cannot read byte 5000 of a file by address. It asks a controller (through a driver) to move blocks of data into RAM first. We call it secondary storage.

        CPU can execute this directly:      CPU can NOT execute this directly:

    RAM  ◄──── CPU                     Disk ──► controller ──► RAM ──► CPU
    ROM  ◄──── CPU                          (I/O, blocks, slow) 
─────────────────────────────────────────────────────────────────────────────────────
            RAM                        DISK / SSD
    (Primary Memory)                (Secondary Storage)
    ─────────────────           ────────────────────
    • Volatile                  • Persistent
    • Fast (GBs/sec)            • Slower (100s MB/sec)
    • Small (8–64 GB)           • Huge (500GB–8TB)
    • Holds RUNNING programs    • Holds FILES at rest
    • Accessed by CPU           • Accessed via I/O controllers

  • Why is the disk "I/O"? (The hard disk is NOT memory)

    • Because the CPU does not directly manipulate it like RAM. The CPU talks to a disk controller through I/O instructions; data is transferred into RAM first, then the CPU reads it from RAM.

      CPU ──(I/O request)──► Disk Controller ──► Disk
▲                                            │
└──────(DMA transfer to RAM)◄────────────────┘

    • "Hard disk is not memory" — correct in the strict sense: it's secondary storage, an I/O device. In casual speech people say "memory" loosely; in exams and interviews, be precise.

    • This is why starting a program means loading it from disk into RAM. This is also why RAM size changes how many programs run at once, and disk size changes how much you can keep.

  • Speed: why we need all these kinds

    • Fast storage is small and expensive. Big storage is slow and cheap. Computers use a mix, and programs move data upward before using it.
      Storage Typical access time Size
      Registers under 1 ns bytes
      CPU cache a few ns MB
      RAM around 50 to 100 ns GB
      SSD around 100 µs hundreds of GB
      Hard disk (spinning) around 10 ms TB

  • 🙋 Question: the SSD is fast, why is it still not memory?

    • speed is not the test. The test is how the CPU reaches it. If the CPU needs a controller and a driver to get the data, it is I/O.

  • 🔥 Senior Insight: many devices (UART, GPIO, timers) are reached through memory-mapped I/O. A register of the device appears at a memory address, so a normal read or write talks to hardware. This is exactly how embedded C controls a pin. Large transfers use DMA so the CPU does not copy bytes one by one.

I/O Devices
  • Everything that isn't CPU/RAM is I/O:
  • Input: keyboard, mouse, camera, sensors, network card
  • Output: screen, speaker, printer
  • Both(Input & Output): disk, network, USB
  • All I/O ultimately goes through the OS — your program doesn't touch hardware directly (that's the whole point of Chapter 5).

2. Chapter 2 — Types of Computing Systems (General purpose vs embedded System)

  • There are two big families. The difference is purpose, not size.

    • General purpose:

      • built to run any program the user installs. Laptop, desktop, server, and in practice a phone.
      • can do anything but slowly/expensively.

    • Embedded:

      • built into a product to do one fixed job. Washing machine controller, car ECU, smart meter, router, thermostat, sensor node.
      • Embedded does one thing extremely well, cheaply, and reliably.

  • 🔥 Senior Insight: do not define embedded by "has no OS". A home router runs Linux and is still embedded, because the user cannot install programs on it. A Raspberry Pi running Linux is a general purpose board used as an embedded system. Ask: who decides what runs, and is the job fixed?

  • "Why can't a car's brake controller run Windows?"

    • Because Windows is general-purpose: it's huge, has a scheduler that can pause your code, and is not deterministic (can't guarantee a response within X microseconds). Brake systems need real-time guarantees → RTOS or bare-metal.

  • "Is a smartphone embedded?"

    • Good answer: it is general purpose for the user (apps), and it also contains many embedded systems inside it (modem, camera controller, touch controller).

  • Why this matters for the rest of the lesson

    • The next chapters change depending on which side you are on. Embedded targets often run firmware or bare-metal code with no OS. General purpose targets run OS apps. That one difference decides how you write, build and debug.

Chapter 3 — The Boot Cycle (Computer Pc have ROM)

Chicken-and-Egg Problem (Why ROM?) vs BIOS — Problem & Solution

PROBLEM:

  • CPU needs instructions → instructions on disk → disk needs software → software on disk 🔁
  • To load the OS from disk, you need software. But that software lives on the disk you can't read yet.

SOLUTION:

  • CPU reset vector → ROM (BIOS) → init RAM → read raw disk → load GRUB → load kernel → systemd → apps

WHY ROM:

  • Non-volatile + memory-mapped + zero-software-readable + fixed address

Question Answer
Why can't the CPU load the OS directly? It needs a driver + filesystem to read disk, which are themselves software on the disk → deadlock
Why ROM and not RAM? RAM is volatile and empty at power-on; ROM is non-volatile and readable with no software
What is the reset vector? The fixed address the CPU jumps to at power-on — it points into ROM
Is BIOS an OS? No — it's firmware. It initializes hardware and loads the bootloader, then it's done
What breaks the chicken-and-egg loop? The CPU's hardwired reset vector + the ROM contents (BIOS/UEFI)
Full Boot Cycle
Power → ROM(BIOS/UEFI) → POST → Bootloader(GRUB) → Kernel → initramfs → systemd → Apps

Common Mistakes

  • ❌ Mistake 1: "BIOS loads the operating system"

        ❌ BIOS loads Windows/Linux directly.
    ✅ BIOS loads the BOOTLOADER, which loads the kernel.
    • Why it matters: If you think BIOS loads the OS, you can't diagnose "GRUB not found" vs "kernel panic" — they're different stages.

  • ❌ Mistake 2: "The kernel is the whole OS"

        ❌ The OS = the kernel.
    ✅ The OS = kernel + system libraries + systemd + user-space tools (shell, utilities).
    • Why: The kernel is the core, but ls, bash, and systemd are all user-space programs outside the kernel.

  • ❌ Mistake 3: "RAM is used from the very first instruction"

        ❌ The CPU loads instructions into RAM immediately at power-on.
    ✅ The first instructions execute from ROM; RAM is initialized by BIOS, then used.
    • Why: This is the chicken-and-egg problem — RAM controller must be configured before RAM can be used.

  • ❌ Mistake 4: "GRUB is part of the kernel"

        ❌ GRUB is inside the kernel.
    ✅ GRUB is a separate program on disk that LOADS the kernel.
    • Why: GRUB has its own code, its own config, and runs before the kernel exists.

  • ❌ Mistake 5: "systemd starts first"

        ❌ systemd is the first thing that runs.
    ✅ BIOS → GRUB → kernel → THEN systemd (PID 1).
    • Why: systemd is the first user-space process, but it's the fifth major stage in the boot chain.

  • ❌Mistake 6: "If POST fails, the OS is corrupted"

        ❌ POST failure = OS problem.
    ✅ POST failure = hardware problem (RAM, CPU, GPU).
    • Why: POST runs before any OS code. It tests hardware only.

  • ❌ Mistake 7: "UEFI is just a newer BIOS"

        ❌ UEFI is BIOS version 2.0.
    ✅ UEFI is a fundamentally different firmware architecture (EFI partition, Secure Boot, networking, GUI).
    • Why: This matters for partitioning (GPT vs MBR), bootloader design, and security.
